Normalization Analysis (1NF, 2NF, 3NF)

1. First Normal Form (1NF)

Rule: Each column contains atomic (indivisible) values, and each record is uniquely identifiable with a primary key.

Compliance: In our schema, student details (name, email, phone) and item attributes are stored as atomic fields. Repeating groups (such as multiple claims or lost items) are factored out into dedicated child tables.

2. Second Normal Form (2NF)

Rule: Table is in 1NF and contains no Partial Functional Dependencies (no non-prime attribute depends on a proper subset of a composite candidate key).

Compliance: Every table uses a single surrogate primary key (student_id, item_id, lost_id, found_id, claim_id, return_id). Since all primary keys are single-attribute keys, partial dependencies are mathematically impossible.

3. Third Normal Form (3NF)

Rule: Table is in 2NF and contains no Transitive Functional Dependencies (non-prime attributes depend ONLY on the primary key, i.e., $X \rightarrow Y$ implies $X$ is a superkey or $Y$ is a prime attribute).

Compliance: Student attributes (e.g. department, phone) are NOT duplicated in LOST_ITEM or CLAIM; only the foreign key student_id is referenced. Similarly, item attributes (e.g. category, location) exist only in ITEM and are accessed via relational joins.

Review 1 Viva Preparation (Key Questions & Answers)

Q1: Why did you separate ITEM from LOST_ITEM and FOUND_ITEM?
Answer: To prevent data redundancy and support 3NF normalization. The ITEM entity represents the physical article (name, category, description, physical location), while LOST_ITEM and FOUND_ITEM represent transactional events linking specific students with event timestamps and lifecycles.
Q2: How do you maintain referential integrity when a student or item is deleted?
Answer: We configured foreign key constraints with ON DELETE CASCADE for operational tables (LOST_ITEM, FOUND_ITEM, CLAIM) and ON DELETE RESTRICT for RETURN_RECORD so that legal handover audit logs cannot be accidentally erased.
Q3: What happens when an item claim is approved?
Answer: When an admin approves a claim, our system executes a transactional update: the claim's status is set to 'Approved', the found item's status transitions to 'Claimed', and any other pending claims for that same item are automatically marked as 'Rejected'.
Q4: What indexes did you create and why?
Answer: We created B-tree indexes on STUDENT(email) (unique lookups), ITEM(category), ITEM(location), and status fields (status, claim_status) to accelerate multi-condition search queries across large datasets.
